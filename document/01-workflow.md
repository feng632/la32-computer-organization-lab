# 三人协作与整合流程

## 1. 文件负责人

| 人员 | 主责文件 | 必须交付 |
|---|---|---|
| A | 新建 `myCPU/csr.v`、`myCPU/csr_defines.vh`、`tests/team/csr/` | CSR 模块、独立测试、运行说明与结果 |
| B（仓库持有者） | `ID_stage.v`、`EXE_stage.v`、`MEM_stage.v`、`WB_stage.v`、`mycpu_head.v`、`tests/team/pipeline/` | 指令与异常通路、冲突保护、除法恢复测试 |
| C | `IF_stage.v`、`mycpu_top.v`、SoC/工程配置、`tests/team/integration/`、本目录集成记录 | 跳转、顶层连接、联合测试、bit 与报告 |

路径均相对于仓库根目录。测试目录目前不存在，由相应人员在实施阶段创建。A 的稳定计数器放在 `csr.v` 内；若拆文件，模块对外接口仍保持 02 不变。

不直接改别人负责的文件。需要跨文件修改：说明具体需求，由负责人修改，或在合并请求中明确授权一次协同修改。B 维护公共总线布局，A 维护 CSR 编号与枚举定义，C 维护顶层连接。

## 2. 分支与权限

- `main`：阶段已确认版本和团队资料；B 确认合入。
- `integration-ex8-ex9`：C 维护，允许尚未完成阶段验收的整合版本，状态必须写明。
- `feat/csr`、`feat/exception-pipeline`、`feat/fetch-integration`：A/B/C 开发分支。
- 三人各有自己的本地克隆。仓库持有者自行在 GitHub 添加协作者；这些文档不等于已经授予 GitHub 权限。
- 不强推共享分支，不移动通过标签，不覆盖别人的未提交修改。

完整公开环境的共同起点是 06 指定的提交，不是仅含阶段源码的原始实验分支。C 建立集成分支后，先组织 A/B/C 各提交接口骨架，再合成共同起点；此步骤不能让三个人同时各改一份 `mycpu_top.v`。

## 3. 开发循环

1. 开始任务前同步集成分支，读取当前接口版本和未关闭问题。
2. 只做一个可解释的小功能；涉及接口，先更改文档并获得另两人的明确确认。
3. 自测：语法/连接检查和本功能测试。用替代模块必须标注，不作为整体验收依据。
4. 提交代码、测试文件和 07 交付记录，发起合并请求。说明接口是否变化。
5. 相关接口另一方审查；C 合入集成分支，运行本次针对性联合测试。
6. 失败时由 C 记录第一处差异并分派；模块负责人修复、自测，C 重跑失败案例。
7. 每天至少一次同步“提交、已测内容、阻塞点、下一项交付”，不要求每天合入不完整功能。

提交开发进度允许测试未通过，但必须标为 WIP；不能将未通过的提交标成“可集成”。

## 4. 合并门槛

| 状态 | 要求 | 能否称为实验通过 |
|---|---|---|
| 开发中 | 说明未完成项目 | 否 |
| 模块自测通过 | 可复现的本模块测试、真实结果 | 否 |
| 针对性集成通过 | 真实 A/B/C 模块连接，相关短程序通过 | 否 |
| 本地阶段通过 | 课程镜像、参考轨迹匹配，完整仿真结束通过 | 仅本地功能 |
| 线上通过 | 保存提交版本、bit 哈希、任务号、得分 | 仅对应线上结果 |
| 时序通过 | 保存本次实现报告，建立/保持及约束均检查 | 单独声明 |

ex8/ex9 完整镜像包含以前的指令测试时，以实际覆盖清单作为回归证据；无需每次合并重复运行 ex1～ex7 全套镜像。未覆盖的关键旧功能用定向测试补齐。

## 5. 接口变更规则

接口版本 TEAM-ABI-1.0 已冻结为本次实施起点。变更提出人填写 07 模板，说明原因、影响、迁移提交与测试；A/B/C 三方确认后，先更新 02 和 `interface-v1.json`，再同步修改连接。破坏兼容时升级主版本，不把新布局仍称为 1.0。

文档依赖顺序：课程要求/指令语义 → 本目录设计 → 接口表 → RTL。发现架构语义冲突要公开纠正文档，不能以“文档规定”为由保留已确认的功能错误。

## 6. 集成职责不等于包办修复

C 提供最小复现、第一处错误、提交号和环境；A 修 CSR，B 修流水线，C 修 IF/连接/环境。跨模块问题共同定位。B 作为仓库持有者负责阶段批准，不接管 A/C 的开发与测试任务。
