# P3 分支预测性能统计

## 1. 这个测试回答什么问题

P2 判的是"对不对"：开了预测器以后，写回结果是否与期望一致、错误路径有没有架构副作用。
P3 判的是"值不值"：周期降了多少、预测准到什么程度、失败是哪种原因。

两者共用 `../bp_p2/asm.py` 汇编器和行为级指令/数据 RAM 的测试骨架，但 TB 独立，
`tb_bp_p2.sv` 一行未改，P2 的既有结论不受 P3 影响。

### 与 ex8 / ex9 的分工（重要）

课程的 ex8、ex9 是**课程测试**，指令流里没有为分支预测设计的压力场景，
它们只能证明"加了预测器没把原来能跑的程序跑坏"。

| 层次 | 手段 | 能证明 | 不能证明 |
|---|---|---|---|
| 架构回归 | ex8 47/47、ex9 58/58（BP=0 / BP=1 各一遍） | 既有功能未被破坏 | 预测器在不在工作 |
| 扩展功能 | `bp_fetch` 77 项、`bp_p2` 4 程序 | 命中/失败/目标冲突/错误路径无副作用 | 有没有性能收益 |
| 性能收益 | **本目录 P3** | 周期、准确率、命中率、失败原因分解 | — |

评测平台上没有针对扩展实验的专项任务，这是客观事实，不假装有。
线上 ex8 / ex9 任务的作用是"带预测器的 bit 仍能拿满分并过时序"，属于兜底；
扩展实验的收益必须由本目录的本地统计数字说话。

## 2. 统计口径

所有观察点都取自 DUT 内部真实信号，不做事后估算：

| 观察点 | 来源 |
|---|---|
| ID 实际发射 | `u_id_stage.normal_fire`（已排除异常与 ertn） |
| 分支分类 | `u_id_stage.is_branch` / `is_cond` |
| 实际跳转与目标 | `u_id_stage.actual_taken` / `br_target` |
| 该指令被取指时的预测结果 | `u_id_stage.fs_to_ds_bp_r` = `{hit, taken, next_pc}` |
| RTL 认定的失败 | `u_id_stage.bp_redirect_valid` |
| 被丢弃的已取指令 | `bp_redirect_valid && u_if_stage.fs_valid` |

定义：

- `cycles`：`resetn` 释放到程序写结束标志之间的拍数，与 P2 日志中的 `cycles` 同一口径。
- `inst (to ID)`：进入 ID 的指令数（`fs_to_ds_valid && ds_allowin` 有效拍）。
- `committed (WBs)`：WB 级有效指令拍数（`u_wb_stage.ws_valid`），**这是"提交"的口径**。
- `ipc` = `inst / cycles`；`cpi` = `cycles / committed`。
  两者分母不同，报告 CPI 时用 `committed`，不把进入 ID 的数量当提交数。
- **预测正确** `ok`：预测后继 == 实际后继。包含"BTB 无条目且实际不跳"这种默认直行猜对的情况。
- 失败按原因四分类：
  - `cold`：BTB 无条目（含 tag 冲突被挤掉）而实际跳转；
  - `dir`：命中且预测跳，实际不跳（过度预测）；
  - `tgt`：命中且预测跳、实际跳，但目标地址不同；
  - `miss`：命中但预测不跳（2-bit 状态 < 2），实际跳。
- **一致性自检**：`redirect` 必须等于四类失败之和。不等时 TB 打印 `[WARN] consistency check FAILED`。
  本次 12 次运行全部通过。
- `fs drop`：纠正发生时 IF 级已取但被丢弃的指令数（实测，不是估计）。
- `non_branch_redirect`：**非分支指令**触发的纠正数。正常应为 0；
  非 0 说明表项把普通指令带偏了，是预测器或索引算法的缺陷信号，单列不并入分支准确率。

## 3. 运行方法

```powershell
# 仓库根目录，PowerShell 执行策略若受限需先放开当前进程
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
./tests/team/integration/bp_p3/run_bp_p3.ps1
```

可选参数：`-VivadoBin`、`-Python`、`-OutputDir`。

脚本流程：`asm.py --selftest` → 汇编 `bp_p2/prog/*.s` 与 `bp_p3/prog/*.s` →
编译两套顶层（`BP_ENABLE=0` 对照、`BP_ENABLE=1` 开预测）→ 每个程序每种配置各跑一遍 →
先判功能（写回是否等于 `expect`），再收集统计 → 输出汇总表与 `summary.csv`。

功能项任一失败即 `RESULT: FAIL`，统计数字此时不采信。
输出目录已存在时脚本改用带时间戳的新目录，不删除任何已有文件。

## 5. 结论

1. **周期收益恰好等于纠正次数减少量，每次纠正值 1 拍。**
   - p1_loop：`50→43`，减少 7 拍；`redirect 10→3`，减少 7 次。
   - p5_nested：`118→102`，减少 16 拍；`redirect 24→8`，减少 16 次。
   - 其余四个程序 `redirect` 不变，周期一拍不少。这是 2 级流水（IF/ID）的结构决定的：
     失败预测只能丢 1 条已取指令，代价 1 拍，所以收益上限就是纠正次数本身。

2. **收益完全来自时间局部性（BTB 命中），不是"预测"这件事本身。**
   p1_loop 命中 9 次、p5_nested 命中 26 次，才有收益。
   一旦每条分支只执行一次（p2_wrong、p3_conflict、p6_chain 的 `btb_hit` 全为 0），
   准确率与 BP=0 完全相同，周期也完全相同——**零收益，但也零损失**，说明加入预测器
   对一次性代码路径没有副作用代价。

3. **间接跳转目标变化拿不到收益。**
   p4_jirl 里 `jirl` 目标在 t1/t2 之间切换，命中 5 次但纠正次数仍是 7，
   只是失败原因从"全 cold"变成"5 cold + 2 dir"。周期 43 拍未变。
   这印证了"表项只记最后一次目标"的局限性，也是后续可以改进的方向（目标地址预测）。

4. **BP=0 的"准确率"不是预测能力。** BP=0 时预测后继恒为 `pc+4`，
   `ok` 只统计到"实际不跳"的分支（p1_loop 11 条分支里只有 1 条不跳 → 9.1%）。
   对照基线正确读法是"等价于永不预测跳转"，不能拿来当作"预测器不如不预测"的证据。

5. **CPI 用提交数算，与 IPC 不同分母。** p1_loop `1.471 → 1.265`，p5_nested `1.341 → 1.159`，
   与周期降幅一致。报告时不要混用 `inst`（进 ID）和 `committed`（过 WB）两个分母。

6. **普通指令纠正数全为 0。** 12 次运行无一例非分支纠正，说明预测器表项不会把普通指令
   带向错误地址；自检也据此改为 `branch_fail + non_branch == redirect`。

7. **测试覆盖不能代表真实程序。** 上表的程序都只有几十条指令，样本量小，
   p1_loop / p5_nested 的 13~14% 是循环密集型的上限值，不能外推到真实工作负载。
   要给出有代表性的数字，需要跑课程完整测试程序的分支剖面，
   这需要把统计逻辑接进 `soc_verify` 的 `tb_top`（见下节）。
